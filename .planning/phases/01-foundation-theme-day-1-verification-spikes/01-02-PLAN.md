# Plan 01-02: Dexie Database Schema, Consent Gate, Permissions & Dual-Mode Rate Limiter

## Objective
Implement the Dexie.js 4.4.6 client-side database schema with UUID primary keys and front-loaded secondary indexes, seed/reset utilities, the global first-run consent modal mounted in `app/layout.tsx` requesting `navigator.storage.persist()`, background sync of theme changes to Dexie `settings` table, non-blocking just-in-time permission helpers, and the dual-mode in-memory / Upstash rate limiter.

## User Rules & Context
- **SHELL:** zsh
- **Package Manager:** pnpm
- **Primary Keys:** String UUIDs (`crypto.randomUUID()`) for `walks`, `entries`, `notes`, `speechCache`; explicit string `'user_settings'` for `settings` table (D-04).
- **Secondary Indexes:** Front-loaded in v1 schema: indexed `startedAt`, `endedAt` on `walks`; `walkId`, `timestamp`, `verified` on `entries`; `walkId` on `notes` (D-06).
- **Seed/Reset:** Provide explicit manual dev controls: `seedDatabase()` and `clearDatabase()` (D-05).
- **Consent Gate:** Full-screen modal mounted in `app/layout.tsx` on first launch explaining data handling, saving timestamped version `1.0` in Dexie, calling `navigator.storage.persist()`, and gating walk/capture access (CONS-01, CONS-02, CONS-03).
- **Theme Background Sync (D-07):** Theme state transitions in `localStorage` and `theme-toggle` synchronize in the background to Dexie `settings` table (`db.settings.put({ ...currentSettings, theme })`).
- **Rate Limiting:** IP token bucket with in-memory fallback for local dev and Upstash Redis for production (RATE-01).

<action>
1. Install optional Upstash dependencies for production rate limiting:
   `pnpm add @upstash/redis @upstash/ratelimit`
2. Create `lib/rate-limit.ts`:
   - Implement `MemoryRateLimiter`:
     - Token bucket algorithm keyed by `${endpoint}:${ip}`.
     - Configurable token refill rate and burst capacity.
     - Evicts stale buckets older than 24 hours to prevent memory leaks in dev server.
     - Provides `reset()` method for test clearing.
   - Implement dual-mode factory:
     - Detects `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN`.
     - If both exist, uses Upstash Redis sliding window limiter.
     - If missing, logs informational notice once: `[RateLimit] Using in-memory rate limiter (dev mode)` and falls back to `MemoryRateLimiter`.
   - Endpoint Quotas:
     - `identify`: 30 requests / 24 hours per IP
     - `facts`: 60 requests / 24 hours per IP
     - `transcribe`: 30 requests / 24 hours per IP
     - `speak`: 40 requests / 24 hours per IP
     - `route`: 40 requests / 24 hours per IP
     - `spike`: 60 requests / 24 hours per IP
   - Export `checkRateLimit(req: Request, endpoint: RateLimitEndpoint)`:
     - Extracts client IP using headers: `x-forwarded-for`, `x-real-ip`, or `127.0.0.1`.
     - Returns:
       ```typescript
       export interface RateLimitResult {
         success: boolean;
         limit: number;
         remaining: number;
         reset: number; // Unix timestamp in seconds
         headers: Record<string, string>;
       }
       ```
     - Standard HTTP rate limit headers:
       - `X-RateLimit-Limit`
       - `X-RateLimit-Remaining`
       - `X-RateLimit-Reset`
3. Write unit test / test harness in `scripts/test-rate-limit.ts` verifying burst limiting, token exhaustion, and `X-RateLimit-*` header emission.
</action>
